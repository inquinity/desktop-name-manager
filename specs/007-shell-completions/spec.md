# Feature Specification: Shell Completions (Feature F1)

**Feature Directory**: `specs/007-shell-completions`

**Created**: 2026-10-09

**Status**: Implemented and released in 0.1.2 (build 3), 2026-10-09

**Target release**: 0.1.2

**Input**: User description: "CLI completions for bash and zsh for our commands, with the available monitors added dynamically, as git completes branch names." Depends on display aliases (spec 006, released in 0.1.1), which `--display` completes too.

## Clarifications

### Session 2026-10-09

- **Q: Which shells?**
  - **A**: bash and zsh, for both command names (`dnm` and `desktop-name`). fish is out of scope for now (the parser can generate it; it is a later, small addition).
- **Q: How are completions produced?**
  - **A**: By `swift-argument-parser`, already in the product: it generates the static part (commands, options, fixed values) and calls the tool back for dynamic values. Each shell's script runs the command name the user typed with the parser's hidden `---completion` arguments, and the tool prints the candidates. No new dependency, no private interface, no second program.
- **Q: What does Tab offer?**
  - **A**: Commands and options (static). The fixed values of `--style`, `--position` and `--size` come from the same lists the tool validates against; `--color` offers `light` and `dark` (a `#RRGGBB` value can still be typed). `--display` offers `main`, the connected displays' names and the aliases that would resolve (spec 006), computed when Tab is pressed. `dnm alias <name> <display>` offers `main` and display names but no aliases (display-only mode of the single resolver). `dnm alias --remove <name>` offers every stored alias, including ones for displays that are away. A new alias name, a label, `--desktop` and `--json` values are not completed.
- **Q: Which aliases are offered for `--display`?**
  - **A**: Only the ones `--display` would accept now: the display is connected and no connected display's own name overrides the alias. Offering one that would fail, or that points somewhere else, would be worse than offering nothing.
- **Q: Where do the rules for the candidates live?**
  - **A**: With the resolver (`DisplayResolver.completionCandidates`), so the names and aliases a person can type and the ones Tab offers cannot drift apart. Every candidate must resolve.
- **Q: What may a completion do?**
  - **A**: Read only. It lists the connected displays and reads the stored aliases. It needs no permission, makes no network connection, switches nothing, changes no wallpaper, and never creates or writes the store. Any failure (an unreadable or newer store, no displays) offers nothing and prints no error, so a completion never writes into a person's command line.
- **Q: How do the scripts reach the user's shell?**
  - **A**: The release zip carries scripts generated by the release binary itself during the build (so they always match that version); the Homebrew cask installs them with its `zsh_completion` and `bash_completion` stanzas, one registration per command name. Without Homebrew, `dnm --generate-completion-script zsh|bash` prints the same script (README). Homebrew's own requirement still applies: the shell must load Homebrew's completion folders (README links the Homebrew instructions).
- **Q: What about bash?**
  - **A**: The generated script runs under the bash 3.2 that macOS ships (checked with a simulated Tab on 2026-10-09). The usual setup is Homebrew's bash with `bash-completion@2`; `bash_completion` files from the cask are loaded the way every Homebrew completion is.
- **Q: Does this change any stored data or release gate?**
  - **A**: No stored data. The release zip gains a `completions/` folder, so spec 005's zip-contents rule (FR-005) and the release procedure's zip check change.

## User Scenarios & Testing

### User Story 1 - Complete commands, options and fixed values (Priority: P1)

As a user, I want Tab to finish `dnm` commands, options and the fixed values of `--style`, `--position`, `--size` and `--color`, so that I do not have to remember them.

**Independent Test**: In zsh or bash with the completions loaded, type `dnm s<Tab>` (offers `set`, `show`) and `dnm set x --style <Tab>` (offers `plain`, `halo`, `frosted`).

**Acceptance Scenarios**:
1. **Given** the completions are loaded, **When** the user presses Tab after `dnm `, **Then** every command is offered.
2. **Given** `dnm set x --position `, **When** Tab is pressed, **Then** the six positions are offered, exactly the values `--position` accepts.
3. **Given** the command is typed as `desktop-name`, **When** Tab is pressed, **Then** it completes the same way.

---

### User Story 2 - Complete display names and aliases (Priority: P1)

As a user with several monitors, I want `--display <Tab>` to offer the monitors that are connected now and my aliases, as git offers branch names.

**Independent Test**: With two displays and the alias `desk`, `dnm show --display <Tab>` offers `main`, both display names and `desk`.

**Acceptance Scenarios**:
1. **Given** displays "Built-in Retina Display" and "DP" and alias `desk` (for the built-in display), **When** Tab is pressed after `--display `, **Then** `main`, `Built-in Retina Display`, `DP` and `desk` are offered; a name with spaces is inserted so the shell treats it as one word.
2. **Given** an alias for a display that is not connected, or one that a connected display's name overrides, **When** Tab is pressed, **Then** that alias is not offered.
3. **Given** `dnm alias work <Tab>`, **Then** `main` and the display names are offered, and no aliases.
4. **Given** `dnm alias --remove <Tab>`, **Then** every stored alias is offered, including ones for absent displays.
5. **Given** a display was just plugged in or an alias was just set, **When** Tab is pressed again, **Then** the new candidates appear (nothing is cached).

---

### User Story 3 - Install the completions with the tool (Priority: P2)

As a Homebrew user, I want the completions to be installed with `dnm`, and removed with it, so that I set nothing up by hand.

**Independent Test**: `brew install --cask inquinity/tap/desktop-name-manager`, open a new shell, and Tab completes `dnm`; `brew uninstall --cask` removes the completion files.

**Acceptance Scenarios**:
1. **Given** the cask is installed, **Then** the zsh and bash completion files for `dnm` and `desktop-name` are in Homebrew's completion folders.
2. **Given** the cask is uninstalled, **Then** those files are gone.
3. **Given** `dnm` was not installed by Homebrew, **When** the user runs `dnm --generate-completion-script zsh` (or `bash`), **Then** a complete script for that shell is printed to standard output.
4. **Given** a release is built, **Then** its zip contains the completion files generated by that binary, and the release procedure checks them.

## Edge Cases

- **No displays connected, an unreadable store, a store newer than the tool understands**: no candidates, no output on standard error, exit 0.
- **Two displays with the same name**: the name is offered once; choosing it is then ambiguous, as `--display` already says.
- **Names with spaces or control characters**: control characters are replaced as everywhere else; spaces are quoted or escaped by the shell script.
- **Typed prefix**: the shell filters the candidates; the tool offers all of them.
- **Slow or failing display lookup**: the lookup is the same one `dnm displays` uses (about 20 ms); there is no timeout logic and no caching.
- **zsh's completion cache**: zsh reuses the cache it built earlier, and a `.zshrc` that runs `compinit -C` never rescans, so after installing, Tab completes file names until the cache is rebuilt (`rm -f ~/.zcompdump*; compinit`). The README says so; it is shell behavior, not something the tool can fix.
- **Old completion script, newer binary**: the script only calls back into whichever `dnm` is on the path with the parser's fixed arguments, so a script older than the binary offers old commands but never fails.
- **Alias `desk` vs a display named `desk`**: the display wins in `--display` (spec 006); only the display name is offered once.

## Requirements

### Functional Requirements

- **FR-001**: The tool MUST provide completion for bash and zsh, for the command names `dnm` and `desktop-name`.
- **FR-002**: Commands and options MUST be completed. The fixed values of `--style`, `--position` and `--size` MUST be taken from the same enumerations the tool validates against, never from a second list; `--color` MUST offer `light` and `dark`.
- **FR-003**: `--display` (in `set`, `remove`, `undo` and `show`) MUST offer, computed when asked: `main`, the connected displays' names, and the aliases `--display` would accept (display connected, not overridden).
- **FR-004**: `dnm alias`: the display argument MUST offer `main` and the connected displays' names only; with `--remove` the name argument MUST offer every stored alias; a new alias name MUST NOT be completed.
- **FR-005**: The rules for candidates MUST live in one place with the display resolver (`DisplayResolver.completionCandidates`); every candidate MUST resolve through the resolver (a shared name is ambiguous, as before).
- **FR-006**: A completion MUST be read-only: no permission, no network, no switching, no wallpaper change, and it MUST NOT create or write the store. Any failure MUST offer nothing and print nothing on standard error.
- **FR-007**: Candidates MUST NOT contain control characters.
- **FR-008**: `dnm --generate-completion-script bash|zsh` MUST print the script for that shell (the parser's built-in option; it MUST stay available and documented).
- **FR-009**: The release zip MUST contain the zsh and bash completion files, generated by the release binary during `build`; the release procedure MUST fail if they are missing, empty, or do not register both command names.
- **FR-010**: The cask MUST install them with `zsh_completion` and `bash_completion` stanzas, one registration per command name, and uninstalling the cask MUST remove them; the cask test in the release procedure MUST check both.
- **FR-011**: The README MUST say how completions arrive (with the cask, or by `--generate-completion-script`), what the shell needs to load them, and what Tab offers; the release notes and spec 005's zip contents rule MUST be updated.

---

## Success Criteria

- **SC-001**: Tab offers every command, every option of a command, and the accepted values of `--style`, `--position` and `--size`, in zsh and bash.
- **SC-002**: `--display <Tab>` offers exactly `main`, the connected displays and the usable aliases, and every offered value is accepted by `--display` (or reported as ambiguous when two displays share a name).
- **SC-003**: A completion changes nothing on disk (no store is created), needs no permission, and prints nothing on standard error, including when it fails.
- **SC-004**: After `brew install --cask`, a new shell completes `dnm` and `desktop-name`; after `brew uninstall --cask` it does not, and the completion files are gone.
- **SC-005**: `just test` and `just periphery` pass.

## Open question: turning completions on once an installer package ships (needs a spike)

Added 2026-10-10 at the maintainer's request; **not researched yet**. Today completions arrive with the Homebrew
cask, which installs the files (FR-010), and `dnm --generate-completion-script zsh|bash` prints them for anyone else
(FR-008). The question is what happens when the tool is also (or instead) installed from a signed installer package
(`.pkg`), which the maintainer expects to need later because of Gatekeeper:

- The maintainer's understanding, to be verified: a notarization ticket cannot be stapled to a bare binary or a zip
  (spec 005, FR-005), so Gatekeeper must check online on first run, while an installer package can be stapled
  properly. If that holds, then a design in which `dnm` itself edits the user's shell configuration to enable
  completions (as some other command-line tools do) runs into the first-run check of an unstapled binary.
- So: **how are completions turned on after an installer package installs the tool?**

The spike has to answer, with evidence, at least:

1. Which locations can a package install completion files into, and are they on the default completion search path of
   macOS's zsh and bash, and of Homebrew's? If a location works with no configuration, no command is needed.
2. If a command is needed, what does the installed binary have to be (stapled, installed by the package) to run it
   without a Gatekeeper prompt, and does the answer differ from a binary run from a downloaded zip?
3. Should `dnm` ever write the user's shell configuration (a dotfile)? What consent, what exact line, how to see it
   and how to undo it; and what the constitution allows (reversibility, no undocumented preferences, App Store goal).
4. How completions are removed on uninstall, given that a package has no uninstall step of its own.
5. How the package and the cask coexist (the same files from two sources) and what `dnm check` reports.
6. What `--generate-completion-script` still serves.

The answer decides whether the package build needs a post-install script, an extra `dnm` subcommand, or nothing, and
so it must be settled before the package is specified; it blocks no current release.

## Assumptions

- The parser's generated scripts and its hidden `---completion` call convention stay as in the pinned version (1.8.2); an upgrade of the parser re-checks this through the contract tests.
- The user's shell loads Homebrew's completion folders (zsh: Homebrew's `site-functions` on `fpath` before `compinit`; bash: `bash-completion@2` sourced), as for any Homebrew completion.
- Completions are generated for the one architecture the release builds (arm64); the scripts themselves do not depend on it.
- fish, completing `--desktop` numbers, and completing label text are out of scope.
