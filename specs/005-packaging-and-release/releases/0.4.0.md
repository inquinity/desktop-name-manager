# Release 0.4.0: gate record

The menu-bar app (spec 014, roadmap M2): a Mac app that labels the Desktop on screen from the menu bar, with the same
labels and files as `dnm`. The release now installs the app and `dnm` together (`dnm` runs from inside the app;
spec 005 amendment, [../amendment-app.md](../amendment-app.md)). `dnm` itself is unchanged. Written by
`scripts/release.sh` and the maintainer; committed after publishing (FR-017). Contains no credential, personal path
or identifier.

## Release

- Version: 0.4.0, build set by `just release` (tag `v0.4.0`, commit "Release 0.4.0 build N")
- Run by: maintainer, with Claude Code
- A minor release: the app is new; `dnm` behaves as in 0.3.0 apart from spec 015 (a Desktop showing macOS 27's
  stand-in for a dynamic wallpaper is refused, exit 3; see `docs/release-notes/UNRELEASED.md`); the store format is
  unchanged. The download is now `desktop-name-manager-0.4.0-arm64.zip` (it held `dnm-<version>-arm64.zip` before).

`docs/release-notes/0.4.0.md`, composed by `just release` from `docs/release-notes/UNRELEASED.md`.

## Review notes

Release range `v0.3.0..main` (2026-11-22), a code review and a security review by separate fresh agents, read-only.

- Security: no high or medium findings. Low: Apple's notarization log prints to the terminal on a failure (not
  recorded here; do not paste it into a public issue); the record's UUID-shape hygiene scan should run over this file
  once its procedure log is filled; `DNM_STORE_DIR` is honored by the app as by `dnm` (Clean Up still deletes only
  tool-named files); the Accessibility note in the cask applies to `dnm --desktop` only.
- Code: no high findings; the store and manifest format are unchanged, so the app and dnm 0.3.0 share one store.
  Medium, handled: (3) "dnm behaves exactly as before" was too strong (spec 015 and clearer error messages changed
  its wording and refuse some files earlier; exit codes are unchanged): README and release notes now say so;
  (4) the download's name and layout changed (the app holds `dnm`): the release notes now say where `dnm` is.
  Medium, for the maintainer: (1) spec 015 hard-codes the path of macOS's default-wallpaper stand-in
  (`/System/Library/CoreServices/DefaultDesktop.heic`, compared by path, never opened), which CLAUDE.md's "no
  undocumented system files, not even read-only" rule does not carve out (spec 015 Q1 records the approval);
  (2) the refusal applied on every macOS version, so a user on macOS 26 who really chose the stock default would be
  refused with a message that blames dynamic wallpapers; the maintainer decided on 2026-11-22 to narrow it to macOS
  27 and later (spec 015 Q3), and to test macOS 26 after the release, through `brew install`. Low: the app icon art under `Resources/App/AppIcon.iconset/`
  has not been checked for personal content by a reviewer; no app-level test uses the stand-in.
