# Release 0.2.2: gate record

Several displays in one command (spec 010, roadmap F3): `set`, `remove` and `undo` act on every display named, in
order, checking every display before the first change and stopping at the first failure with the displays already
changed and the `dnm undo` for them. Also a new version format (`0.2.2 build 6`, and `0.2.2 build 6 (<commit>)` for
builds from source), a build number that moves on every build, and the version moving on right after a release
(spec 005 FR-003 amendment, 2026-11-06). Written by `scripts/release.sh` and the maintainer; committed after
publishing (FR-017). Contains no credential, personal path or identifier.

## Release

- Version: 0.2.2, build set by `just release` (tag `v0.2.2`, commit "Release 0.2.2 build N")
- Run by: maintainer, with Claude Code
- A patch release with no breaking changes: one display behaves as in 0.2.1, `show` still takes one display, and
  no stored data changes (format 3, as in 0.2.1). The `--version` text changes form.
- This is the first release under the new procedure: `just release` takes no segment, and the `record` stage moves
  `Version.xcconfig` to 0.2.3.

## Review notes

### Security review

Opus, fresh context, given only `v0.2.1..main` (2026-11-09). No high-severity finding; the release guarantees hold
(a release is built from a clean tree whose HEAD sets the build number; terminal output and suggested commands are
sanitized and shell-quoted; no personal data in the added lines).

1. Two builds started together could stamp the same build number: the bump was locked, but the stamp read the
   number back afterwards. Fixed: `bump-version.sh build` prints the number it wrote, and the callers use it.
2. Resetting `Version.xcconfig` (which the release build stage's message suggested) lets a later build reuse a
   number. Fixed in wording: numbers are unique per checkout while kept; the message warns that the next build
   would reuse that number.
- Open question, done: the release build stage now checks the signed tag is on HEAD before signing and notarizing.

### Code review

Opus, fresh context, given only `v0.2.1..main` (2026-11-09). `just test` passed for the reviewer.

1. The same build-number race as security finding 1. Fixed (with a test that every caller gets its own number).
2. A rerun of the `record` stage through `just publish` named the next version. Fixed: the stage appends the log
   once and bumps once, so it can be rerun; its error names `scripts/release.sh <version> record`.
3. A Desktop switch during `--desktop` with several displays said "run `dnm undo` if needed" (which means main)
   before the right command. Fixed: it says "run the undo below if needed".
4. A later display failing with nothing changed before it was not named. Fixed: "On DP: ..." (contract §4).
5. Contract §3 listed the label before the displays; the code checks them in 0.2.1's order. Fixed in the contract.
6. Accepted: when a typed display word has a control character, the suggested undo uses the display's name, which
   is ambiguous if two connected displays share it (the command may be refused, or name the other display). Rare:
   it needs a control character in the typed word and two displays with the same name.
7. `tree-state` accepted a staged 7 under an unstaged 6. Fixed: the working tree is compared with the index too.
- Open questions: a failed return to the start Desktop after an error is silent (`try?`; unchanged since 0.2.0,
  left for a later spec); re-checking a display's on-screen state just before its undo is not needed (an undo of
  one display cannot change another's wallpaper).

### Re-review of the fixes

Opus, fresh context, given only `deaf919..23538be` (2026-11-09). The fixes do what they say; no logic regression in
`tree-state`, the record rerun, the tag check or `DisplayBatch` (one display still behaves as a single command).

1. Medium (a regression from the fix): `bump-version.sh` printed its errors on standard output, which the callers now
   capture, so a stale lock or a bad build number failed the build silently. Fixed in `910e504`: every message goes
   to standard error; checked with a stale lock.
2. Low: a new test could pass without an error being thrown. Fixed.
3. Low: the record stage's "no procedure log" hint suggested a rerun that cannot help. Fixed.
4. Nit: the version-script test left a temporary folder behind on failure. Fixed.
- Open question, left for a later spec: with one display and `--desktop` on a display other than main, a Desktop
  switch during the change still says "run `dnm undo` if needed", which means main (unchanged since 0.2.0).
